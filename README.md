# Iron Man — 설비 변경 요청 안전 관문

AI의 설비 변경 요청을 가상 환경에서 검토하고, 담당자가 승인한 명령만 적용하는 프로젝트의 **4인 팀 개발 골격**입니다.

> 현재는 로컬 데모입니다. 실제 PLC·설비가 연결되어 있지 않습니다. 시뮬레이터 v3는 냉각수와의 온도 차이·열용량·펌프 응답을 반영하며 같은 모델로 SQLite의 가상 온도·실제 속도를 수동 시간 진행에 따라 갱신합니다. 계수는 데모 가정으로 현장 데이터로 검증하지 않았습니다. 근거 검토는 기본 모의 응답이며, live 설정 시 팀 작성 규정을 실제 LLM으로 검토합니다. 실시간 문헌 검색은 없습니다. 가상 설비 전용 정책을 통과한 경우 담당자 승인 후 가상 목표 속도를 적용합니다.

## 담당별 시작점

3번 근거·역근거 모듈 구현과 설정은 [에이전트 인계 문서](docs/evidence_eval.md)를 보세요.
기본 모의 데모는 유지하며, `IRON_MAN_EVIDENCE_MODE=live`에서는 팀 작성 규정 3개를
실제 LLM으로 검토합니다. API 키와 모델 ID 설정이 필요하며, 검토 실패·근거 부족은 보류합니다.
현재 시뮬레이터는 팀원의 v3 물리 계산과 지속되는 가상 상태이며, 비모의 결과 승인 정책 미설정 시 서버가 보류합니다.

| 담당 | 폴더 | 다음 구현 |
|---|---|---|
| 1번 | `backend/gateway`, `backend/main.py` | 실제 인증, 통합·배포 |
| 2번 | `backend/simulator` | 계산 모델 보정, 시계열 API 계약 합의, 상태·어댑터 검증 |
| 3번 | `backend/evidence` | 실제 출처 검색, 구조화 LLM 검토, 적용 조건·근거 부족 |
| 4번 | `frontend/src` | 그래프, 출처 확인 UI, 보고서 표현, 발표·영상 |

공통 계약 v1.0은 [팀 연동 계약](contracts/README.md)에 정리되어 있습니다. JSON 예시·상태별 처리·생성 명령을 먼저 확인하세요. Python 원본은 `backend/contracts.py`, 프런트 자동 생성 타입은 `frontend/src/api.generated.ts`입니다. 변경 시 네 담당의 입력·출력을 함께 확인하세요.

## 현재 동작하는 흐름

```text
React → FastAPI → 요청·데모 정책 검사
                 → 모의 근거 검토 → 반례 시험 추가
                 → 합성 열수지 계산 → 위험 차단 또는 승인 정책 미설정 보류
```

- 서버: 요청 생성·평가·승인·거절·가상 실행 경로, 상태 변경 시 재검증, 중복 실행 방지. 현재 비모의 계산 결과에는 승인 경로를 열지 않습니다.
- 평가: 별도 프로세스에서 수행, HTTP 202 후 상태 조회. 기본 동시 2개·90초 제한, 취소·중복 방지·오래된 결과 차단. [평가 작업 안내](docs/EVALUATION.md)
- 화면: 요청 입력, 평가 상태 자동 조회·취소, 조건별 비교 표, 근거 카드, 승인·실행, 처리 기록, 가상 설비 상태와 수동 시간 진행
- 검증: API 통합 테스트, 프런트 타입 검사·빌드, GitHub Actions 구성
- 저장: **SQLite**. 요청·보고서 이력·승인·실행 기록과 가상 설비 상태를 저장합니다. 기본 파일은 `data/ironman.sqlite3`이며, 같은 파일을 사용하는 서버는 한 개만 실행합니다. [저장·복구 안내](docs/STORAGE.md)를 확인하세요.

## Docker로 실행

Docker Desktop/Engine 실행 후 저장소 루트에서:

```bash
docker compose up -d --build --wait
```

화면: http://localhost:8080. 웹·API가 함께 실행되며 DB는 영구 볼륨에 저장됩니다. [Docker 실행·저장·설정 안내](docs/DOCKER.md)를 확인하세요. 외부 공개·HTTPS 배포는 다음 단계입니다.

## Python·Node로 직접 실행

Python 3.11 이상, Node.js 22 이상을 권장합니다. 저장소 루트에서 시작합니다.

터미널 1 — 백엔드:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -c requirements-dev.lock.txt -e '.[dev]'
python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

터미널 2 — 화면:

```bash
cd frontend
npm ci
npm run dev
```

- 화면: http://127.0.0.1:5173
- API 문서: http://127.0.0.1:8000/docs
- 상태 확인: http://127.0.0.1:8000/health

Vite 개발 서버의 `/api` 프록시가 백엔드로 연결합니다. 빌드된 정적 파일을 배포할 때는 별도 `/api` 리버스 프록시가 필요합니다. 외부 공개 배포는 아직 구성하지 않았습니다.

## 현재 계산 결과 확인

초기 가상 상태(60°C·부하 1.0·실제/목표 속도 100%)를 기준으로:

1. 기본 `local-operator` 토큰으로 **60%·300초** 요청 → 최고 온도 정상 약 73.23°C, 효율 저하 약 83.69°C로 한계 초과, 차단.
2. **80%·300초**로 새 요청 → 정상 약 65.88°C, 효율 저하 약 77.27°C로 가상 정책을 통과하면 승인 대기. 담당자 승인 후 가상 목표 속도 적용.
3. 승인·가상 실행 시연은 1번 담당이 명시적인 데모 승인 정책을 합의·구현한 뒤 진행.

60·80% 결과는 합성 상태와 데모 계수에서 계산한 예시이며 현실 안전 기준이 아닙니다. 수정은 새 요청으로 만들며 기존 승인을 재사용하지 않습니다.

v3의 가상 설비는 승인자 토큰 `local-approver`로 수동 시간을 진행합니다. `POST /demo/advance` + `{"seconds_s": 10}`은 현재 목표값을 향해 실제 속도와 온도를 10초 계산하고 저장합니다. `GET /state`로 현재 온도·실제/목표 속도·가상 시간을 읽습니다. 조회나 서버 재시작은 시간을 진행하지 않습니다. `POST /demo/sample`은 관측 시각을 갱신하고, `POST /demo/reset`은 이력을 보존하면서 데모 초기 상태로 되돌립니다. 화면에서도 이 작업을 할 수 있습니다. 상태 진행 후 기존 승인은 실행 전에 재검증해야 합니다. 요청의 `duration_s`는 예측 구간이며 적용 목표값을 자동으로 되돌리지 않습니다.

`local-operator`, `local-approver`는 로컬 데모용 공개 토큰입니다. 운영 인증이 아닙니다. `.env.example`의 환경변수를 셸에서 export하면 변경할 수 있습니다. `.env` 자동 로딩은 하지 않습니다. 실서비스 인증·비밀 관리·사용자 식별은 1번의 후속 구현입니다.

## 구현 시 주의할 경계

- 2번은 계산, 3번은 근거, 4번은 표시, 1번은 판정·실행 권한을 담당합니다.
- 시뮬레이터는 `mock=False`, 근거 검토는 `mock=True`입니다. 서버의 가상 전용 정책은 normal·degraded_cooling 계산과 출처·범위를 확인해 승인 대기/보류/차단을 결정합니다. `unknown` 적용 조건을 현실 설비의 승인 근거로 사용하지 마세요.
- 계산·문서 오류는 보류, 실행 결과 불명은 추가 실행 금지로 처리합니다.
- 실행 예약을 DB에 먼저 저장하고 가상 상태·적용 영수증을 같은 트랜잭션으로 저장합니다. 실행 중 서버 종료는 결과 불명으로 복구하고 자동 재전송하지 않습니다. 실제 장비의 결과 재조정과 다중 worker는 후속 구현입니다.
- 감사 기록은 SQLite에 보존되지만 DB 파일 편집을 막는 변조 방지 저장소는 아닙니다.
- 실제 데이터나 비밀키를 fixtures, Git, Codex 제출 기록에 넣지 마세요.
