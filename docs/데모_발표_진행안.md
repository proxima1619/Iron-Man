# 데모·발표 진행안 — 설비 변경 요청 안전 관문

이 문서는 구현·녹화 시 사용할 대본이다. 아직 실행한 데모나 측정 결과가 아니다. 수치와 성공 여부는 실제 통합 시험 후 확정한다.

## 1. 관객이 기억할 한 문장

“AI의 설비 변경 요청을 먼저 가상 환경에서 시험하고, 반례와 불확실성을 보여준 뒤, 담당자가 검토한 명령만 실행하게 합니다.”

시연 대상은 냉각 펌프다. “절전을 위해 속도를 줄여 달라”는 익숙한 요청이 냉각 효율이 낮아진 상황에서는 위험해질 수 있음을 보여준다.

## 2. 데모 준비물과 역할

| 준비물 | 담당 | 준비 기준 |
|---|---|---|
| 데모 초기 상태·고정 모델·위험 요청·수정 요청 | 2번 | 계산으로 정상·위험 차이를 확인한 입력 세트 |
| 실제 원문이 확인되는 근거와 효율 저하 반례 | 3번 | 출처 ID·원문 위치·적용 조건 포함 |
| 서버 정책·승인 계정·실행 기록 | 1번 | 권한·만료·변경·중복 검사 동작 |
| 시연 화면과 클릭 동선 | 4번 | 비교→근거→수정→승인→실행을 빠르게 이동 |
| 데모 초기화 버튼 | 1·2번 | 데모 전용 기능, 초기화 상태 표시 |
| 실제 동작 녹화와 오프라인 PDF | 4번 | 제출 대상 코드와 일치, 비밀값 노출 없음 |

발표자는 1번, 화면 조작은 4번을 권장한다. 두 사람은 클릭·말하기 순서를 맞춘다. 발표자가 네 명으로 바뀌는 구성은 4분에서 전환 시간이 커지므로 피한다.

## 3. 핵심 데모 세 장면

### 장면 A — 정상 시험에서 놓친 조건을 반례로 추가한다

1. 상단의 “가상 설비 · 합성 데이터” 표시를 보여준다.
2. 준비한 펌프 속도 감소 요청을 입력하고 평가한다.
3. 기본 시험의 변경 전·후 그래프를 보여준다. 이 시점은 **검토 중**이고 아직 승인할 수 없다.
4. 근거 카드에서 냉각 성능 저하 조건과 원문 위치를 보여준다.
5. “이 근거에서 추가된 시험”을 열어 효율 저하 시험 결과를 보여준다.
6. 제한 초과가 확인되면 서버 판정이 차단으로 확정되고 실행이 불가능함을 보여준다.

설명: “기본 조건에서는 문제가 드러나지 않았습니다. 문서의 적용 조건에서 찾은 반례를 추가하자, 같은 요청이 온도 제한을 넘었습니다.”

이 설명은 실제 결과가 그럴 때만 쓴다. LLM은 반례를 찾고, 온도 값은 시뮬레이터가 계산하고, 차단은 서버가 결정한다는 세 역할을 짚는다.

### 장면 B — 수정한 요청을 다시 검증하고 승인한다

1. 미리 계산으로 확인해 둔 더 보수적인 목표 속도로 수정한다.
2. 새 revision으로 기본·추가 시험과 적용 조건을 다시 검토한다.
3. 필수 조건이 확인되면 승인 대기를 보여준다.
4. 담당자 승인 후 실행을 누른다.
5. 가상 설비 어댑터의 적용 응답과 갱신된 명령값을 보여준다.

설명: “수정안도 검증을 다시 받습니다. 담당자가 승인한 이 요청만 가상 설비에 적용됩니다.”

같은 요청의 숫자를 화면에서만 바꾸거나, 이전 승인을 새 요청에 이어 쓰지 않는다. 알려지지 않은 필수 조건이 남아 있다면 수정안도 보류해야 한다.

### 장면 C — 승인 뒤 상태가 바뀌면 실행을 막는다

1. 별도 승인 가능한 요청을 준비해 승인까지 진행한다.
2. 실행 전에 데모 제어로 부하 등 안전 관련 상태를 바꾼다.
3. 실행을 누른다.
4. “상태 변경 · 재검증 필요”와 어댑터 미적용 기록을 보여준다.

설명: “승인은 영구 허가가 아닙니다. 검토 당시 상태가 달라지면, 승인한 요청이라도 다시 확인합니다.”

4분 발표에서는 C를 짧은 장면으로 사용한다. 새로운 평가가 오래 걸리면 미리 준비한 요청을 열되, “미리 검토한 요청”이라고 표시한다. 녹화를 신규 라이브 실행처럼 설명하지 않는다.

## 4. 반드시 별도로 준비할 실패 사례

| 상황 | 화면·서버에서 보여줄 결과 |
|---|---|
| 센서값 누락 또는 노후 | 판단 보류, 필요한 데이터 표시 |
| 관련 문서 없음 | 근거 부족; 필수 적용 조건이면 승인 불가 |
| LLM 시간 초과 | 검토 실패·보류; 성공한 것으로 대체하지 않음 |
| 문서 안의 강제 승인 지시 | 정책·승인 변화 없음, 실행 0건 |
| 승인 API 없이 실행 호출 | 서버 거절, 실행 0건 |
| 동일 실행 ID 재전송 | 중복 적용 없음 |
| 어댑터 응답 유실 | 결과 불명, 상태 확인; 무조건 재실행하지 않음 |

이 전체를 4분에 시연하려 하지 않는다. 시험 표와 결선 부록으로 증거를 남긴다.

## 5. 1차 4분 구성

[공식 대회 안내](https://codex-community-korea.skysplit.chatgpt.site/hackathon/seoul-2026-10)에 따르면 1차는 발표·데모 합계 최대 4분이며 질의응답이 없다. 아래는 3분 50초 종료를 목표로 한 팀 권장안이다.

| 시간 | 내용 | 화면·발표 자료 |
|---|---|---|
| 0:00~0:25 | 사용자와 문제: 냉각 절감 요청이 공정 위험으로 이어질 수 있음 | 슬라이드 1: 요청 하나와 위험 |
| 0:25~0:45 | 해결 구조: 계산·근거 검토·서버 승인 | 슬라이드 2: 짧은 흐름도 |
| 0:45~1:35 | 장면 A: 반례→추가 시험→차단 | 라이브 또는 표시된 녹화 |
| 1:35~2:10 | 장면 B: 수정→재검증→승인→가상 적용 | 데모 |
| 2:10~2:30 | 장면 C: 승인 뒤 상태 변경→실행 거절 | 데모 |
| 2:30~3:00 | 검증 결과·실패 처리·모델 한계 | 슬라이드 3: 실제 시험 표 |
| 3:00~3:25 | 초기 사용자·도입 경로·기대 가치 | 슬라이드 4: 읽기 전용 평가부터 도입 |
| 3:25~3:50 | Codex 활용·검토 과정, 마무리 | 슬라이드 5: 오류 발견과 수정 사례 |
| 3:50~4:00 | 시간 여유 | 추가 설명을 새로 시작하지 않음 |

슬라이드 3에는 실제 실행한 시험 수와 결과, 합성 데이터·단순 모델·실제 설비 미연결을 함께 넣는다. 검증 수치가 부족하면 “위험 감소율”을 만들지 말고 관찰한 요청별 결과를 보여준다.

AI 활용 설명에서는 “문서를 요약했다”에서 끝내지 않는다. 반례가 시험 조건으로 전달되어 결과가 바뀐 지점을 보여준다. 보안 설명은 명령·보고서·상태에 묶인 승인과 실행 거절 화면으로 짧게 증명한다.

## 6. 결선 10분 준비

공식 안내의 결선 제한은 발표·데모·질의응답을 합친 최대 10분이다. 팀 내부로는 발표·확장 데모 6분, 질의응답 약 4분을 권장하되 현장 진행 지침에 맞춘다.

추가 부록은 다음 다섯 장이면 충분하다.

1. 승인 저장 항목과 실행 직전 검사.
2. 모델 식·단위·계수의 출처·검증 범위.
3. 문서 적용 조건과 근거 부족 사례.
4. 정상·위험·보류·실패를 구분한 시험 결과.
5. 현장 도입에 필요한 데이터·연동·운영 과제.

예상 질문과 답변 기준:

- **규칙만으로 할 수 있지 않나?** 사전 규칙은 기본 경계다. AI는 문서의 조건·한계를 찾아 추가 검증 질문을 만들고, 숫자·권한 판정은 검증 가능한 코드가 담당한다고 답한다. 실제 반례 전후 비교를 제시한다.
- **시뮬레이터가 틀리면?** 현재 모델의 범위와 합성 데이터임을 밝힌다. 범위 밖·데이터 부족은 보류하며, 현장 적용에는 실측 비교가 필요하다고 답한다.
- **사람이 승인하면 위험한 것도 실행되나?** 차단·보류는 승인으로 우회되지 않는다. 승인 가능한 보고서에만 승인하고 실행 직전에 다시 검사한다고 설명한다.
- **문서에 공격 지시가 들어 있으면?** 문서 에이전트에 제어 권한이 없고, 출력·시험 조건을 검증한다. 시험한 공격 사례와 결과를 말하며 완전 방어를 주장하지 않는다.
- **실제 설비를 제어했나?** 별도 가상 설비 어댑터로 실행 경로를 검증했으며 실제 PLC 연결은 후속이라고 답한다.
- **어떤 고객이 돈을 내나?** 설비·생산기술 조직을 초기 도입 후보로 제시하고, 과거 요청 평가부터 시작하는 가설이라고 밝힌다. 확인하지 않은 고객 수요·절감률을 확정하지 않는다.
- **자동 복구는 가능한가?** 이번에는 실패 확인과 추가 실행 보류를 구현한다. 실제 복구는 설비별 절차와 별도 검증이 필요하다고 답한다.

## 7. 녹화·장애 대응

1. 제출 후보 코드에서 데모 데이터를 초기화한다.
2. 실제 평가·승인·실행 과정을 녹화한다. 숨은 고정 성공 응답을 쓰지 않는다.
3. 영상에 “가상 설비”, “합성 데이터”, 캐시 사용 시 “캐시 재생”을 표시한다.
4. 원본 영상과 발표 길이에 맞춘 짧은 영상을 보관한다. 대기 구간을 편집하면 편집 사실을 표시한다.
5. 영상·PDF를 오프라인에서도 열어 본다.
6. 네트워크 장애가 나면 “이전 실행 녹화로 전환하겠습니다”라고 알리고 재생한다.
7. 장애 시 추가 시간이 보장된다고 전제하지 않는다.

데모 링크는 심사자가 접근 가능한 주소로 제출한다. localhost만 적은 링크는 다른 기기에서 열리지 않으므로 피한다. 실제 배포 또는 대회가 허용하는 녹화·시연 링크 형식은 별도 제출 안내를 확인한다. 이 계획 작성 단계에서는 배포·영상·PDF가 만들어진 상태가 아니다.

## 8. 제출 직전 확인

- [ ] 발표와 녹화가 최종 심사 대상 코드와 일치한다.
- [ ] 수치가 실제 출력에서 나왔고 실측·합성의 구분이 있다.
- [ ] 4분 리허설 완료, 발표·조작 담당 확정.
- [ ] PDF 폰트·그래프·작은 글씨를 발표 환경에서 확인했다.
- [ ] 데모 링크·원문 링크가 다른 브라우저에서 열린다.
- [ ] 저장소 링크·커밋 SHA·Codex 기록·PDF·데모 링크를 제출했다.
- [ ] 사전 준비와 당일 구현을 구분했다.
- [ ] 17:00 KST 전에 제출 완료 상태를 확인했다.
