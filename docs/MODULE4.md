# 4번 담당 검토 화면 — v3 통합

기준: 로컬 복제본 `1a59bb3d63f5bbcd28aa9e1ad45cb6cf7b955363`의 v3 가상 설비와 서버 승인 정책.

## 구현한 화면과 연결

- 변경 목적·속도·유지 시간 입력과 선택 요청자 연락처.
- 2번 계산의 기존/변경 최고 온도 비교 막대·표와 위험 조건.
- 3번 출처 종류·원문 URL·원문 위치·발행/버전·일치/미확인 조건·반례 연결.
- 모델·정책·가상 실행 범위·합성 데이터 출처·모델 한계 표시.
- 서버 세션에서 승인자 역할 확인, 명령·보고서 해시 확인, 사유와 승인/거절/재시험 요청.
- 비동기 평가 자동 조회·취소, 이전 보고서/승인/이벤트 조회, 인쇄·PDF 저장.
- v3 가상 설비 상태·목표/실제 속도·가상 시간·관측 시각, 수동 시간 진행·관측 갱신·초기화 유지.

계산은 2번, 출처 검토는 3번, 최종 판정·권한은 1번 서버가 책임집니다. 4번이 온도 값이나 승인 가능 여부를 생성하지 않습니다. 현재 API에는 시계열이 없어 최고 온도 막대만 표시합니다. 링크는 HTTP(S)만 허용하며 문서는 텍스트로 표시합니다.

## 서버 정책과 negligible 편차

기존 `backend/gateway/policy.py`의 가상 설비 전용 정책을 유지했습니다. `cooling-demo-v3`, `virtual` 어댑터, 지정 출처, 정상/냉각 저하 시험, 300초 예측, 80°C 제한 등을 기존 서버가 검사합니다. 실제 설비 승인 경로는 없습니다.

`DecisionReport.assessment`는 두 속도의 **최고 온도 절대 차이**를 추가로 요약합니다. `IRON_MAN_NEGLIGIBLE_DELTA_C`에 팀이 합의한 °C 기준을 설정하면 초과 시 `MATERIAL_DEVIATION`으로 지정 승인자의 예외 검토를 요청합니다. 기준 이내도 기존 정책에 따라 담당자의 승인이 필요합니다. 온도 한계·무효 센서·범위 밖·근거 부족은 예외 승인으로 해제하지 않습니다.

기준 기본값은 없습니다. 미설정이면 화면은 `편차 기준 미설정`으로 표시하고 편차에 대한 추가 분류를 하지 않습니다. 기존 v3 정책의 가상 승인 대기는 유지합니다. 이 지표는 **예측-실측 잔차나 TEP 정상 운전의 이상 점수가 아닙니다.** 이상치 기록·잔차 입력 계약은 2번과 별도로 합의해야 합니다.

편차 기준은 보고서 해시에 포함되며, 승인/적용 전 현재 설정과도 비교합니다. 승인 후 명령·상태·모델·보고서·정책·기준 또는 만료가 달라지면 서버가 재검증을 요구합니다. 현재 상태 스냅샷 제한은 60초, 승인 TTL은 300초입니다. v3 관측은 상태 조회만으로 갱신되지 않습니다.

## 역할과 연락처

`GET /session`이 확인한 operator/approver 역할을 표시합니다. 승인·거절은 approver, 재시험 요청은 두 역할 모두 가능합니다. 실제 개인 로그인이나 이메일 소유 인증은 구현하지 않았습니다. 공유 역할 토큰과 HTTPS edge 인증은 기존 구현을 사용합니다. `IRON_MAN_APPROVER_LABEL`은 표시명입니다.

요청자 이메일은 `NewRequest.requester_contact`에 선택 입력하며, 일반 요청·보고서·평가 프로세스에 포함하지 않습니다. 별도 DB 테이블에 저장하고 승인자 전용 `/review-contact`에서만 반환합니다. 주소 소유 여부는 미검증입니다. 토큰은 브라우저 저장소에 저장하지 않습니다.

## 이메일 알림

서버 환경에 `IRON_MAN_APPROVER_EMAIL`, `IRON_MAN_SMTP_HOST`, `IRON_MAN_SMTP_PORT`(기본 587), `IRON_MAN_SMTP_FROM`을 설정합니다. 필요한 경우 SMTP 사용자·비밀번호를 설정합니다. STARTTLS를 사용합니다. 로컬 Python 실행은 `.env` 자동 로딩을 하지 않으므로 셸에서 환경변수를 설정하세요. Compose 변수는 `.env.example`에 정리했습니다. 비밀값은 서버에만 두고 Git에 넣지 않습니다.

평가가 승인 대기가 되면 같은 DB 트랜잭션으로 알림을 기록합니다. 설정이 없으면 `not_configured`, 있으면 `queued`입니다. **자동 발송하지 않습니다.** 승인 담당자가 최신 유효 보고서의 발송 버튼을 누를 때만 지정 주소로 알림을 보냅니다. 이메일은 연락을 위한 알림이며 인증·승인·실행 수단이 아닙니다.

SMTP 접수는 `sent`로 기록하며 실제 수신/열람 완료를 뜻하지 않습니다. 발송 오류·발송 중 서버 종료는 `unknown`으로 남고 자동 재발송하지 않습니다. 이미 접수한 같은 알림 호출은 이전 결과를 반환합니다. 수신 주소·SMTP 설정 변경 후에는 재검증하여 새 알림을 만드세요. 이번 개발 과정에서 실제 이메일은 발송하지 않았습니다.

## DB와 API

기존 SQLite 동적 가상 상태 스키마 v2를 유지한 채, v3 마이그레이션으로 `request_contacts`, `notifications` 테이블을 추가합니다. 기존 보고서·승인·가상 상태는 삭제하지 않습니다. 이 저장소 이전의 별도 v2 개발 초안 DB를 복사해 사용하지 마세요. 단일 서버/worker 제한은 기존과 같습니다.

| API | 권한·역할 |
|---|---|
| GET `/session` | 인증 역할·저장·편차 기준·알림 설정 조회 |
| GET `/requests/{id}/review-contact` | approver에게만 연락처 반환 |
| GET `/requests/{id}/notifications` | approver에게만 알림 이력 반환 |
| POST `/requests/{id}/notifications/{note_id}/send` | approver의 명시적 알림 발송 |
| POST `/requests/{id}/decisions` | 기존 approve/reject + request_retest |

기존 1.0 계약에 선택 필드와 API를 추가했습니다. 엄격하게 추가 필드를 거부하는 소비자는 최신 계약으로 함께 갱신해야 합니다. Python 원본은 `backend/contracts.py`이며 OpenAPI와 프런트 타입을 함께 갱신했습니다.

## 팀이 정할 사항

1. 최종 이상치·예측 잔차 지표와 negligible 기준. 현재 최고 온도 차이는 합성 시연용입니다.
2. 실제 승인자의 개인 인증, 이메일 주소, SMTP 제공자와 개인정보 보존 정책.
3. TEP 구현·정상 기록 구간·초기 상태·제어 입력 매핑·참조/예측 시간축과 새 API 계약.
4. 실제 근거 출처의 적용 조건·미확인 조건과 연결된 반례 시험.

현재 모델은 TEP가 아닌 v3 합성 냉각 모델입니다. 실제 문헌 검색·TEP 다운로드·실측 검증·현실 설비 실행을 완료했다고 설명하면 안 됩니다.
