# 설비 변경 요청 안전 관문 — 팀 개발 계획

작성 기준: 2026-10-09 KST. 4인 팀, 트랙 1 참가, 당일 개발·시연을 위한 권장 계획이다. 이 문서는 구현 지시서이며, 현재 제품이 구현되었거나 설비 안전성이 검증되었다는 보고서가 아니다.

## 1. 우리가 완성할 제품

**AI가 설비 변경을 제안하면, 가상 설비에서 결과를 계산하고 문서의 근거·반례를 확인한 뒤, 담당자가 검토한 바로 그 명령만 실행하도록 통제하는 서비스.**

주 사용자는 설비 운전 담당자와 생산기술 엔지니어다. 데모에서는 “냉각 펌프 속도를 내려 전력 사용을 줄이려는 요청”을 다룬다. 펌프를 너무 줄이면 냉각이 부족해 온도가 상승하는 상황을 보여준다.

완성 장면은 다음과 같다.

1. 사용자가 냉각 펌프 속도 변경을 요청한다.
2. 서버가 요청 권한, 명령 형식, 사전에 정한 안전 규칙을 검사한다.
3. 시뮬레이터가 현재 상태에서 변경 전·후를 계산한다.
4. 근거 에이전트가 관련 문서의 적용 조건을 비교하고, 냉각 효율 저하라는 반례를 발견한다.
5. 서버가 반례를 추가 시험에 반영한다. 정상 조건과 다른 위험이 나타나는지 계산한다.
6. 담당자는 비교 그래프, 근거 원문, 불확실성, 서버 판정을 확인한다.
7. 위험한 요청은 실행하지 않는다. 수정 요청은 새로 검증한다.
8. 승인 가능한 수정안에 담당자가 승인하면, 서버가 명령·상태·버전·승인 유효성을 다시 확인하고 데모용 설비 어댑터에 전달한다.

**모든 실제 설비 적용은 담당자 승인 이후다.** 데모의 실행 대상은 실제 공장이 아닌 별도 가상 설비다. 화면에는 항상 “가상 설비 데모 · 실제 장비 미연결”을 표시한다. 시뮬레이션 통과와 담당자 승인도 현실 설비 안전을 보증하지 않는다.

### 이번에 반드시 구현할 것 — P0

- 설비 1개: 냉각 탱크와 펌프를 단순화한 모델.
- 명령 1종: `set_pump_speed`, 단위 `%`와 유지 시간 명시.
- 현재 상태 스냅샷과 모델·안전 규칙 버전 고정.
- 변경하지 않은 경우와 변경한 경우의 동일 조건 비교.
- 정상·효율 저하 시험, 센서 데이터 불량·지연에 대한 보류 처리.
- 실제 LLM을 이용한 문서 주장 추출, 적용 조건 비교, 반례 후보 생성.
- 반례 후보를 허용된 시험 변수로 변환하여 추가 계산하는 연결.
- 서버의 차단·보류·승인 대기 판정, 담당자 승인·거절, 실행 전 재확인.
- 승인된 명령만 받는 가상 설비 어댑터와 실행 결과 기록.
- 출처·실측 여부·불확실성을 보여주는 화면, 회귀 시험, 녹화 데모.

### 시간 여유가 있을 때 — P1

- 외부 문헌 실시간 검색, 더 많은 설비·시험 조건.
- 센서 오류를 동적으로 주입하는 추가 시뮬레이션.
- 실행 후 예측과 관측의 차이를 감시하는 확장 데모.
- 사전 정의한 추가 시험 묶음을 실행하는 도입 전 평가 화면.
- 하드웨어 LED 등 승인 여부를 보여주는 단순 시각화.

### 후속 개발로 남길 것

실제 PLC·펌웨어 복제, 실제 공장 연결, 현장 데이터 기반 보정·검증, 산업용 안전 인증, 고가용성, 현장 인증 체계, 변조 방지 저장소를 이용한 감사 기록, 설비별 안전 정지 절차.

첨부 기획의 “자동 되돌리기”와 “위변조할 수 없는 기록”은 당일 구현 완료로 주장하지 않는다. 물리적 결과는 명령을 되돌린다고 복구되지 않을 수 있다. 이번에는 실행 실패·불확실 상태를 기록하고 추가 실행을 보류한다. 일반 DB 기록이나 해시만으로 기록의 불변성이 보장되지는 않는다.

## 3. 역할과 연결 구조

| 담당 | 최종 책임 | 가장 먼저 만들 것 | 최종 인계물 |
|---|---|---|---|
| **1번 / 안철민** | 전체 흐름, 서버 판정, 승인과 실행 권한, 통합·제출 | 공통 데이터 형식과 요청 상태 흐름, 모듈 모의 응답을 연결한 API | 동작하는 서버, 승인·실행 검사, 통합 시험 결과, 실행·제출 문서 |
| **2번** | 가상 설비, 상태·데이터, 수치 계산과 모델 한계 | 동일 입력에 동일 결과를 내는 `simulate()` | 시뮬레이터, 데모 설비 어댑터, 상태 스냅샷, 모델 설명, 계산 시험 |
| **3번** | 문서 출처, 적용 조건, 반례와 근거 부족 | 출처가 있는 문서 묶음과 구조화된 `review_evidence()` | 근거 검토 모듈, 출처 목록, 반례 시험 후보, 실패 처리와 평가 기록 |
| **4번** | 담당자의 이해와 판단, 보고서·승인 화면, 발표 자료 | 고정 샘플을 읽는 비교·근거·승인 화면 | 연결된 UI, 보고서 표현, 발표 PDF, 데모 영상·시연 대본 |

의사결정 권한은 다음과 같이 구분한다.

- **2번은 계산한다.** “허용 온도를 초과했다”는 계산 결과를 내고 승인 권한은 갖지 않는다.
- **3번은 근거와 반례를 제안한다.** 명령, 안전 규칙, 승인 상태를 수정하지 않는다.
- **4번은 설명하고 판단을 전달한다.** 버튼 상태만으로 실행 권한을 통제하지 않는다.
- **1번은 정책으로 판정하고 실행을 통제한다.** 모델이 계산한 숫자나 문서의 주장 내용을 임의로 고치지 않는다.
- **담당자는 승인 가능한 요청에 대해 승인·거절한다.** 차단된 요청을 승인 버튼으로 우회하지 않는다.

권장 구현은 Python 서버·시뮬레이터·근거 모듈 + React/TypeScript 화면 + SQLite다. 팀의 익숙한 기술이 있으면 그것을 우선하되, 이번에는 네 개의 독립 배포 서비스로 나누지 않는다. 백엔드 내부 함수로 2·3번을 연결하면 운영 부담이 줄어든다.

```text
4번 화면 → 1번 API → 권한·형식·안전 규칙 검사
                        ├─ 2번: 기본 시뮬레이션
                        └─ 3번: 근거·적용 조건·반례 후보
                                  ↓
                        1번: 후보 검증·중복 제거·개수 제한
                                  ↓
                        2번: 승인된 조건으로 추가 계산
                                  ↓
                        1번: 최종 판정·보고서 버전 확정
                                  ↓
4번 보고서 → 담당자 판단 → 1번 승인 저장·실행 전 재확인
                                  ↓
                        2번의 가상 설비 어댑터 → 결과 기록
```

기본 시뮬레이션과 문서 검토는 동시에 수행해도 된다. 추가 시험은 최대 1회 묶음, 최대 3개 조건으로 제한한다. 처리 중에는 승인할 수 없고, 근거·계산 결과가 확정된 보고서만 승인 대상으로 삼는다.

## 4. 개발 시작 후 첫 30분에 네 명이 합의할 내용

각자 구현하기 전에 아래 내용을 하나의 공통 파일에 적는다. 1번이 초안을 만들고, 2번은 단위·변수, 3번은 근거·시험 조건, 4번은 화면에 필요한 필드를 확인한다.

1. 설비 ID와 명령 이름: `cooling-demo-01`, `set_pump_speed`.
2. 입력: 현재 펌프 속도, 목표 속도, 유지 시간, 변경 목적.
3. 상태: 온도, 부하, 냉각 효율, 가동 모드, 센서 시각·품질.
4. 단위: 온도 °C, 시간 s, 펌프 속도 %, 부하·효율은 무차원 비율로 명시.
5. 안전 규칙: 허용 명령·범위, 온도 제한, 상태 유효 시간, 승인 만료 시간. 수치는 데모용 설정임을 표시한다.
6. 결과 상태: 처리 중 / 차단 / 보류 / 승인 대기 / 승인 완료 / 재검증 필요 / 실행 중 / 완료 / 실패·결과 불명.
7. 시연 사례: 위험 요청 하나, 수정 후 승인 가능한 요청 하나, 승인 뒤 상태 변경 하나.
8. 고정 샘플 JSON: 네 명이 이 파일로 먼저 연결한다. 모의 응답에는 `mock=true`를 표시한다.

특정 목표 속도가 안전하다고 먼저 정해 화면에 넣지 않는다. 2번이 계산으로 사례를 찾고, 모델·초기 상태·요청을 고정한다. 실제 결과가 나오기 전에는 발표용 온도·절감률도 확정하지 않는다.

## 5. 1번 — 요청·관문 서버 / 안철민

### A. 무엇부터 시작할 것인가

**첫 목표는 다른 모듈이 미완성이어도 요청→보고서→승인→가상 실행이 한 번 이어지는 골격이다.**

1. 저장소 등록 상태를 확인하고 폴더·공통 계약·샘플을 만든다.
2. 요청 생성, 상세 조회, 평가 시작, 판단 저장, 실행 API를 만든다.
3. 2·3번의 고정 모의 응답을 연결해 4번이 즉시 개발할 수 있게 한다.
4. 요청별 ID, 요청 revision, 상태 전이와 감사 이벤트를 저장한다.
5. 이후 모의 응답을 실제 2·3번 함수로 교체한다.

### B. 반드시 구현할 기능

**요청 검사**

- 요청자 역할을 서버가 확인한다. 데모용 고정 계정을 써도 서버 세션 등 서버가 확인하는 정보에서 역할을 얻는다. 브라우저가 보낸 `role=approver`를 그대로 믿지 않는다.
- 허용된 명령·단위·값만 받는다. NaN, 무한대, 잘못된 단위, 범위 밖 값은 거절한다.
- 상태 스냅샷은 서버가 2번 어댑터에서 읽고 저장한다. 사용자 입력을 센서 실측처럼 취급하지 않는다.

**평가 조율**

- 요청 revision, snapshot, model version, policy version을 확정해 2·3번에 전달한다.
- 3번의 반례는 알려진 시험 종류·변수·허용 범위만 받는다. 자유 코드나 임의 네트워크 요청을 실행하지 않는다.
- 기본·추가 시험 완료, 문서 검토 상태, 모델 범위와 데이터 품질을 종합한다.
- 시간 초과나 오류를 “문제없음”으로 처리하지 않는다. 미완료 상태와 사유를 반환한다.

**판정 규칙**

| 조건 | 서버 판정 | 다음 행동 |
|---|---|---|
| 권한 없음·금지 명령·사전 안전 규칙 위반 | 차단 | 사유 표시, 실행 불가 |
| 이번 검토에 채택한 관련 시험에서 한계 초과 | 차단 | 조건 수정 후 새 revision으로 재검증 |
| 필수 데이터 누락·노후 센서·모델 범위 밖·필수 검토 실패 | 보류 | 부족한 정보 표시, 실행 불가 |
| 안전 판단에 필요한 적용 조건을 확인하지 못함 | 보류 | 해당 조건 확인 또는 요청 수정 |
| 필수 시험과 조건 확인 완료, 위반 없음 | 승인 대기 | 담당자가 승인 또는 거절 |

논문 수가 적다는 이유만으로 자동 차단하거나, 논문이 많다는 이유로 승인 가능하게 만들지 않는다. 사전 정책에서 필수로 정한 조건이 확인되었는지를 본다. 문헌의 부재와 명백한 위험 발견을 구분한다.

**승인·실행 관리**

- 승인은 `request revision + command digest + snapshot digest + model version + policy version + report digest`에 연결한다.
- 서버가 정규화한 데이터에서 digest를 계산한다. 클라이언트가 보낸 해시를 권한 근거로 쓰지 않는다.
- 승인자, 판단 시각, 만료 시각, 판단 이유를 저장한다.
- 보고서·명령·모델·규칙이 바뀌면 기존 승인으로 실행할 수 없다.
- 실행 직전에 최신 상태를 다시 읽는다. P0에서는 안전 관련 필드의 변경을 보수적으로 재검증 사유로 삼는다. 센서 수집 시각만 갱신되는 것과 값·품질·가동 모드 변화는 구분한다.
- 승인 확인·미사용 확인·실행 예약을 DB 트랜잭션 등으로 원자적으로 처리한다. 승인 두 번 클릭, 실행 API 중복 호출로 두 번 실행되지 않게 한다.
- 어댑터는 같은 `execution_id`를 중복 적용하지 않는다. 응답이 유실되면 같은 ID로 상태를 조회하고, 새 ID를 만들어 무조건 재시도하지 않는다.
- 실패·응답 불명을 완료로 쓰지 않는다. 결과를 확인할 때까지 추가 실행을 보류한다.

### C. API 초안

| API | 용도 | 주의점 |
|---|---|---|
| `POST /requests` | 구조화된 명령 등록 | 원문과 정규화 명령을 분리 저장 |
| `POST /requests/{id}/evaluate` | 현재 revision 평가 | 상태 스냅샷을 서버가 획득 |
| `GET /requests/{id}` | 진행·결과·판정 조회 | UI는 여기서 받은 상태를 표시 |
| `POST /requests/{id}/decisions` | 승인·거절 | 승인자 권한과 report revision 검사 |
| `POST /requests/{id}/execute` | 승인된 요청 실행 | 현재 상태·만료·중복·digest 재검사 |
| `POST /requests/{id}/revisions` | 조건 수정 | 이전 결과·승인을 이어 쓰지 않음 |
| `GET /requests/{id}/events` | 검토·승인·실행 기록 조회 | 비밀키·불필요한 원문 개인정보 제외 |

### D. 무엇이 되면 완성인가

- 정상 요청 1건이 실제 2·3번 모듈과 연결되어 승인 후 가상 설비에 적용된다.
- 승인 없이 실행 API를 직접 호출해도 서버가 거절한다.
- 승인 후 명령·상태·모델 버전 변경, 승인 만료, 이중 실행을 검사한다.
- 모듈 실패가 보류로 표시되고 실행되지 않는다.
- 각 요청에 입력·계산·근거·판정·승인·실행 기록이 연결된다.
- 팀원이 README만 보고 실행할 수 있고 심사 링크에 접속할 수 있다.

**인계물:** API 명세, 서버 실행 명령, 공통 계약, 통합 테스트 결과, 최종 제출 목록. 전체 발표의 핵심 주장과 제출은 1번이 최종 확인한다.

## 6. 2번 — 샌드박스·시뮬레이터

### A. 무엇부터 시작할 것인가

**첫 목표는 그래프가 아니라 재현 가능한 계산 함수다.**

1. 단일 냉각 탱크 모델과 상태 변수·단위를 정의한다.
2. `simulate(command, snapshot, scenarios, model_version)`을 만든다.
3. 같은 초기 상태에서 “기존 속도 유지”와 “요청 속도로 변경”을 각각 계산한다.
4. 정상 조건과 냉각 효율 저하 조건을 넣는다.
5. 시간별 온도, 최고 온도, 제한 초과 여부·시점, 모델 범위 여부를 반환한다.

### B. 모델 수준과 데이터

당일에는 단순 열수지 모델로 시작한다. 예를 들어 시간에 따른 온도 변화는 유입 열량과 냉각으로 제거되는 열량의 차이에서 계산하고, 펌프 명령이 냉각에 반영되는 지연을 둔다. 정확한 식·계수·시간 간격·초기 상태는 `model_card.md`에 기록한다.

- 모델 계수를 특정 위험 장면마다 다르게 바꾸지 않는다. 공통 모델과 명시적인 시나리오 조건으로 결과 차이를 만든다.
- 전력 모델이 없으면 “전력 20% 절감” 같은 수치를 내지 않는다. 목적은 절감 요청이고, 이번에 직접 검증한 결과는 온도·명령 허용 여부로 제한할 수 있다.
- 실측 데이터가 없으면 모든 센서·기록을 합성 데이터라고 표시한다.
- 개발 때 사용한 합성 데이터와 별도 보류 데이터를 비교해도 이는 구현 확인이며 현실 설비 정확도 검증은 아니다.
- 실측 기록을 실제 확보한 경우에만 별도 구간과 비교해 오차·조건·표본 수를 보고한다.
- 예측 범위를 보여주려면 어떤 매개변수 범위를 변화시켰는지 밝힌다. 임의 범위를 통계적 95% 신뢰구간이라고 부르지 않는다.

### C. 필수 시험과 출력

| 시험 | 바꾸는 내용 | 필요한 반환값 |
|---|---|---|
| 정상 | 기본 부하·효율 | 변경 전·후 온도 시계열과 한계 초과 여부 |
| 효율 저하 | 동일 명령, 낮은 냉각 효율 | 최고 온도·초과 시점, 반례 출처 ID |
| 센서 불량 | 센서 품질을 invalid로 표시 | 입력 부적합, 계산 불가 사유 |
| 통신 지연 | snapshot 시각을 오래된 상태로 설정 | 상태 만료 정보; 판정은 1번이 수행 |
| 모델 범위 밖 | 정의한 부하·온도 범위를 벗어남 | `out_of_domain`, 부족 조건 |

센서 불량·통신 지연을 동적 물리 모델로 구현하지 않았다면 “오류 상황의 입력 검증을 구현했다”고 표현한다.

결과에는 `run_id`, 시나리오 ID, 입력 digest, model version, 단위, horizon, dt, 시계열, 지표, 범위 판정, 데이터 출처 유형을 포함한다. 값이 없으면 0으로 채우지 말고 null과 사유를 반환한다.

### D. 가상 설비 어댑터

- 샌드박스는 복사한 상태를 계산하며, 데모 설비의 현재 상태를 변경하지 않는다.
- 별도 어댑터는 1번의 실행 경로에서만 호출된다. 브라우저와 근거 에이전트가 직접 호출할 수 없게 한다.
- `read_state()`, `apply_command(execution_id, command)`, `get_execution(execution_id)`를 제공한다.
- P0에서는 백엔드 내부 객체·함수로 구현해 외부 쓰기 엔드포인트를 만들지 않아도 된다.
- 승인 전에는 데모 설비의 명령값이 바뀌지 않고, 승인 후에는 적용 응답과 읽어 온 상태가 기록되어야 한다.
- 데모 초기화·고장 주입은 데모 전용 제어로 분리하고 실행 감사 기록과 섞이지 않게 표시한다.

### E. 무엇이 되면 완성인가

- 같은 입력·버전으로 반복 실행하면 같은 결과가 나온다.
- 변경 전·후 비교가 같은 초기 상태와 같은 외란에서 계산된다.
- 정상과 효율 저하 결과의 차이를 설명할 수 있다.
- 냉각 강화 시 온도가 낮아지는 등 기본 방향성과 시간 간격 변경에 대한 안정성을 확인한다.
- 예외 입력을 처리하며 3번이 제안한 허용된 조건을 추가 실행할 수 있다.
- UI에 쓰일 숫자는 모두 계산 결과에서 나온다.

**인계물:** 함수·어댑터, 모델 카드, 초기 상태 파일, 재현 가능한 시나리오, 시험 결과. 4번에게 그래프 데이터 형식, 1번에게 오류·범위·버전 규칙을 전달한다.

## 7. 3번 — 근거·역근거 검토 에이전트

### A. 무엇부터 시작할 것인가

**첫 목표는 검색 서비스 전체가 아니라, 원문으로 확인할 수 있는 근거 카드와 추가 시험 하나다.**

1. 냉각·펌프·운전 조건과 관련된 공개 문서 3~5개를 선정하고 실제 내용을 확인한다.
2. URL, 제목, 발행처, 버전·발행일, 절·페이지·문단 위치, 이용 조건을 기록한다.
3. 문서가 어떤 주장을 지지하고 어떤 조건·한계를 제시하는지 짧게 정리한다.
4. LLM에 요청·현재 상태·문서 발췌를 전달해 구조화된 결과를 받는다.
5. 결과가 원문과 일치하고 실제 출처 ID를 가리키는지 검사한다.

MVP는 준비된 문서 집합에서 검색해도 된다. 화면에는 “사전 수집 문서 검색”이라고 표시한다. 실시간 인터넷 검색을 구현하지 않고 구현했다고 표현하지 않는다. 적합한 제조사 자료를 확보하지 못하면 팀 작성 데모 운전 규정을 사용할 수 있지만, 실제 제조사 매뉴얼이나 논문처럼 제시해서는 안 된다.

### B. AI가 실제로 할 일

- 요청의 기대 효과와 검증 질문을 추출한다.
- 지지 근거, 반대 근거, 동일 문서의 한계와 예외를 찾는다.
- 문서의 설비 종류·운전 범위·냉각 조건을 현재 모델·상태와 비교한다.
- 적용 가능 / 일부 일치 / 불일치 / 확인 불가를 구분하고 이유를 적는다.
- “효율 저하 조건에서도 온도 제한을 지키는가?”처럼 추가 검증 질문과 시험 후보를 만든다.
- 근거가 없으면 “근거 부족”, 문서 처리가 실패하면 “검토 실패”를 구분한다.

여러 에이전트 프로세스를 만드는 것은 필수가 아니다. 하나의 모듈 안에 지지·반례 검토 단계를 두고 합쳐도 된다. 서로 다른 이름의 에이전트가 같은 주장을 반복하는 것보다 적용 조건과 원문 위치가 확인되는 것이 중요하다.

### C. 출력 계약

근거 카드마다 다음을 반환한다.

| 필드 | 내용 |
|---|---|
| `evidence_id`, `source_id` | 보고서·시험과 연결하는 ID |
| `claim` | 원문에 근거한 주장 |
| `stance` | support / counter / limitation |
| `locator`, `excerpt` | 원문 위치와 짧은 발췌 |
| `applicability` | applicable / partial / mismatch / unknown |
| `matched_conditions`, `missing_conditions` | 일치·불일치·미확인 조건 |
| `proposed_test` | 허용 시험 ID와 변수 변경 후보, 근거 ID |

문서에 냉각 효율의 수치가 없다면 LLM이 특정 수치를 문헌값처럼 만들지 않는다. 시험용 수치를 선택한 경우 `parameter_origin=demo_assumption`으로 표시하고 2번이 모델 범위 안인지 확인한다.

### D. 신뢰 경계와 실패 처리

- 문서는 근거 데이터다. 문서 안의 “규칙 무시”, “승인 처리”, “이 명령 실행”을 시스템 지시로 취급하지 않는다.
- 에이전트에 승인 API, 실행 어댑터, 안전 규칙 변경 권한을 주지 않는다.
- 존재하지 않는 source ID, 원문에 없는 인용, 허용되지 않은 시험 변수는 결과 검증에서 거부한다.
- 문서 검토 시간 초과 시 필수 검토를 건너뛰어 승인 가능하게 만들지 않는다.
- 장애 대비 캐시는 입력·문서 버전·모델 버전과 연결하고 화면에 “캐시 재생”이라고 표시한다. 기존 응답을 신규 검토 결과로 제시하지 않는다.

### E. 무엇이 되면 완성인가

- 지지·반례·한계·근거 부족 사례가 구분된다.
- 각 카드에서 원문 위치를 확인할 수 있다.
- 실제 LLM 출력의 반례 후보가 1번 검증을 거쳐 2번 추가 시험에 반영된다.
- 근거가 현재 설비에 맞지 않으면 확인 불가·불일치로 표시한다.
- 문서에 악성 지시를 추가한 시험에서 명령·정책·승인이 바뀌지 않는다. 결과는 시험한 사례의 범위로만 주장한다.

**인계물:** 문서 목록·출처, 검토 함수, 스키마, 출력 샘플, 시험 후보, 평가 기록. 문서의 단순 요약이 아니라 “이 근거가 왜 여기 적용되거나 적용되지 않는가”를 제공한다.

## 8. 4번 — 보고서·승인 화면 / 발표·데모

### A. 무엇부터 시작할 것인가

**첫 목표는 샘플 JSON 하나로 담당자가 변경 내용·위험·다음 행동을 이해할 수 있는 화면이다.**

1. 요청 입력과 결과 화면을 한 페이지로 만든다.
2. 1번 공통 샘플로 진행 상태, 비교 그래프, 근거 카드, 판정 영역을 구현한다.
3. 모의 데이터 표시를 붙이고, API가 준비되면 실제 응답으로 교체한다.
4. 차단·보류·승인 대기·재검증 필요·실행 실패를 모두 디자인한다.
5. 동작 화면이 나오면 바로 영상 초안을 녹화하고 발표 자료를 작성한다.

### B. 화면에서 반드시 답할 여섯 질문

| 사용자 질문 | 보여줄 정보 |
|---|---|
| 무엇을 바꾸는가? | 설비·명령·현재값→목표값·유지 시간·목적 |
| 어떻게 달라지는가? | 변경 전·후 온도 그래프, 동일 축, 한계선, 단위 |
| 언제 위험해지는가? | 정상·효율 저하 조건별 결과, 초과 시점·계산 불가 사유 |
| 왜 그렇게 판단했는가? | 근거 카드, 적용 조건, 원문 링크·위치, 실행 기록 |
| 무엇이 불확실한가? | 합성 데이터, 단순 모델, 미확인 조건, 모델 범위 |
| 지금 무엇을 해야 하는가? | 서버 판정, 승인·거절·수정·재검증 행동 |

상단에는 서버 판정과 한 줄 이유를 크게 배치한다. “조건 수정 후 재검증 권고”는 행동 안내이고, 승인 가능 여부는 서버의 별도 필드로 결정한다. 위험 시험이 있는 요청에 승인 버튼을 활성화하지 않는다.

### C. 자연어 설명

- 핵심 숫자·상태·권고는 서버 결과를 그대로 사용한다.
- P0는 검증된 템플릿으로 설명해도 된다. 생성형 요약은 3번의 실제 AI 검토 결과를 바탕으로 덧붙이는 P1로 둔다.
- LLM 요약을 추가하면 실제 존재하는 metric ID·evidence ID를 참조하게 하고, 없는 숫자나 “안전 보장” 표현을 제거한다.
- 생성 실패 시 서버 판정과 구조화된 정보를 그대로 보여준다.

표현 예시: “정상 조건에서는 온도 제한을 넘지 않았지만, 냉각 효율 저하 시험에서는 초과했습니다. 현재 요청은 차단되었습니다. 목표 속도를 수정해 다시 검증하세요. 결과는 합성 데이터와 데모 모델에 기반합니다.”

이 문장은 실제 시험 결과가 그러할 때만 표시한다. 결과가 달라지면 설명도 바뀌어야 한다.

### D. 승인과 실행 UX

- 승인 시 대상 명령·보고서 revision·유효 시간을 보여준다.
- 승인은 판단 기록, 실행 완료는 어댑터 응답 확인 이후로 구분한다.
- 상태 변경으로 승인 무효가 되면 이전 그래프를 최신 결과로 보이지 않게 한다.
- 중복 클릭은 UI에서 막되, 최종 중복 방지는 1번 서버가 수행한다.
- 소스 열기, 시나리오 비교, 수정 후 재검증이 발표 중 적은 클릭으로 가능해야 한다.
- 재생 데모·모의 응답·라이브 결과는 눈에 보이는 라벨로 구분한다.

### E. 무엇이 되면 완성인가

- 코드 설명 없이 화면만 보고 요청·위험·권고를 이해할 수 있다.
- 모든 그래프·숫자·근거가 실제 연결된 모듈 응답에서 나온다.
- 승인·거절·수정·오류 상태가 서버 상태와 일치한다.
- 원문 링크가 열리고, 데모 링크를 다른 브라우저에서도 확인할 수 있다.
- 4분 안에 시연할 수 있으며 녹화 영상과 최종 PDF를 준비했다.

**인계물:** UI, 사용자 동선, 발표 PDF, 데모 영상, 리허설 시간 기록. 발표 수치는 2번, 근거 표현은 3번, 승인·실행 표현은 1번에게 확인받는다.

각 테스트는 입력, 기대값, 실제값, 통과 여부, 관련 로그, 코드 SHA를 남긴다. 수행하지 않은 것은 미실행으로 표기한다. API 거절뿐 아니라 어댑터가 실제로 적용되지 않았는지 함께 본다.

오탐·미탐을 이야기하려면 미리 정한 데모 사례 집합과 기대 분류를 별도로 두고 비교한다. “위험 사례를 얼마나 놓쳤는가”와 “정상 사례를 얼마나 불필요하게 막았는가”를 함께 보고한다. 보류는 통과·정확한 차단으로 섞지 않고 따로 센다. 같은 시뮬레이터가 만든 정답으로 검사한 결과는 제품 흐름 평가이지 현실 안전 성능 평가가 아니다.

보고할 수 있는 지표는 시험 통과 수/실행한 시험 수, 위험·정상·보류별 건수, 반례 추가 전후 판정 변화, 미승인 실행 거절 수, 전체 처리 시간, LLM 호출 수·비용이다. 숫자는 실제 측정 후 적고, 표본이 작으면 분모도 반드시 표시한다.

## 12. 심사에서 설명할 내용과 담당

| 심사 항목 | 보여줄 근거 | 책임자 |
|---|---|---|
| 문제 정의·필요성 | 냉각 절감 요청의 위험, 담당자의 문서·조건 비교 부담 | 1번 |
| AI 판단·해결 방식 | 문서에서 반례 추출 → 추가 시험 → 실제 판정 변화 | 3번 |
| 작동 결과물 | UI→서버→계산→승인→가상 적용의 연결 | 1·4번 |
| 검증·개선 | 정상·위험·정보 부족·동작 실패 시험, 발견 오류와 수정 전후 | 1번 취합, 전원 |
| 도입 가능성 | 제조업 설비팀의 읽기 전용 평가 도입 → 검증 후 승인 연동 계획 | 1번 |
| Codex 활용 과정 | 구체적인 작업, 발견한 오류, 사람의 검토·수정·통합 기록 | 전원 |

도입 가능성은 가설로 설명한다. 초기 도입은 과거 요청 재생과 읽기 전용 평가로 시작하고, 모델 정확도·현장 규칙·권한 체계를 확인한 뒤 실제 제어 연동을 검토한다. 구매자 후보는 제조사의 설비·생산기술 조직, 협력 후보는 설비 통합 업체다. 인터뷰·계약이 없으면 고객 검증을 완료했다고 말하지 않는다.

단순 임계값 검사와의 차이는 “문서의 적용 조건에서 추가 시험을 찾아내는 AI”와 “검토한 요청에만 유효한 서버 승인”을 함께 보여주는 데 있다. 규칙 검사·기본 시뮬레이션만 실행한 결과와 반례를 추가한 결과를 비교하면 AI의 기여를 설명하기 쉽다. 성능 우위는 실제 비교 범위로 한정한다.

Codex 기록은 각자 다음 다섯 항목으로 남긴다: 맡긴 작업 / 만들어진 결과 / 확인 방법 / 발견한 오류와 수정 / 관련 커밋·시험. 토큰 사용량이나 코드 양을 성과로 대체하지 않는다. API 키와 비공개 데이터는 제출 기록에서 제외한다.
